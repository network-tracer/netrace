# Labs

A lab is an ordinary `.netrace` project with a `lab` section: the starting
topology, a Markdown brief, and tasks whose checks netrace runs against the
simulated network every time the topology changes. Open one from
**File → New from Lab…** (⌥⌘N) or the Lab tab; each opens as a new, untitled
copy, so the bundled lab is never changed.

The 20 bundled labs live in `labs/`. They're generated by
`scripts/make-labs.py` (run it from the repository root after editing), and
each has a `.solution` script that `cargo test -p netrace-labs` plays through
the real command line to prove the lab starts unsolved and can be finished.

## Writing a lab by hand

Add a `lab` object to a project's `project.json`:

```json
"lab": {
  "title": "Static routes",
  "topic": "Routing",
  "brief": "R1 and R2 only know their own networks. Add a **static route** on each.",
  "tasks": [
    {
      "title": "R1 has a route to 192.168.2.0/24",
      "detail": "`ip route 192.168.2.0 255.255.255.0 10.0.0.2`",
      "hint": "The next hop is R2's address on the link between them.",
      "checks": [
        { "check": "route", "device": "R1", "network": "192.168.2.0", "prefix_len": 24, "source": "static" }
      ]
    },
    {
      "title": "PC1 can ping PC2",
      "checks": [{ "check": "ping", "from": "PC1", "to": "PC2" }]
    }
  ]
}
```

`brief`, `detail` and `hint` take inline Markdown (bold, italics, `code`).
`detail` shows under the task while it's the current one; `hint` only when
the student asks. A task is done when all its checks pass.

Devices are named as the student sees them. Interfaces can be written short
(`g0/1`, `fa0/3`, `Vlan10`); labels and feedback show them as IOS
abbreviates them (`Gi0/1`).

## Checks

| `check` | Fields | Passes when |
|---|---|---|
| `cabled` | `a`, `b`, optional `a_port`, `b_port` | A cable joins the two devices (on those ports) |
| `interface_up` | `device`, `interface` | The interface is up/up |
| `address` | `device`, optional `interface`, `address`, `prefix_len` | The interface (or, with no interface, the end device) has that address |
| `gateway` | `device`, `gateway` | An end device's default gateway |
| `ping` | `from`, `to` (name or address), optional `succeeds: false` | A 4-packet ping gets a reply (or doesn't) |
| `route` | `device`, `network`, `prefix_len`, optional `source` (`connected`, `static`, `ospf`) | The routing table has the prefix |
| `vlan` | `device`, `vlan`, optional `name` | The VLAN exists (with that name) |
| `access_port` | `device`, `port`, `vlan` | An access port in that VLAN |
| `trunk` | `device`, `port` | The port is a trunk |
| `ospf_neighbors` | `device`, `count` | That many full OSPF adjacencies |
| `stp_root` | `device`, `vlan` | The device is the root bridge for the VLAN |
| `dhcp_lease` | `device` | The end device got a DHCP address (not 169.254) |
| `config` | `device`, `contains` | A running-config line contains the text (case-insensitive) |

Checks look at the simulated result rather than at how it was configured,
so any correct answer passes. A failing check explains itself in the
student's terms; a failing ping quotes the simulation's account of where
the packet was dropped.

## Solution scripts

`labs/NN-name.solution`, one step per line:

```
R1: enable                        # a line typed at R1's console
@ip PC1 192.168.1.10/24 192.168.1.1   # set an end device's address (and gateway)
@dhcp PC1                         # switch an end device to DHCP
@cable PC1 FastEthernet0 SW1 FastEthernet0/1
```

Console lines follow renames, so after `Router: hostname HQ` the next line
is `HQ: …`.
